# Echo Pact 小管家与提炼记忆层路线图

> 状态：施工基线 v1，尚未开始实现小管家。
>
> 制定时间：2026-10-05（成都）
>
> 当前代码基线：`main` / `4c5e5d8b9d8ff29c6ccfae8e3b4dba90d6ff9a19`

## 1. 为什么需要这一层

Echo Pact 当前的 records-v1 路径已经能可靠保存和追查原始记录，并通过
确定性的词面、时间、来源、角色、对话位置和有限规则完成有界召回。继续修复
具体错题仍然有价值，但只靠增加规则，会逐渐遇到三个上限：

1. 同一件事换一种自然说法后，字面锚点可能消失；
2. 一个生活问题常同时包含人物、事件、时间、关系和回答形式，单轮查询难以兼顾；
3. 规则越多，交互和回归面越大，局部修复更容易影响已有能力。

下一阶段不是用模型替换 Echo，而是在确定性证据层前后增加一个受约束的
“小管家”：模型负责理解和规划，Echo 负责证据与边界，最终使用者负责判断和表达。

## 2. 不变的底线

以下条款高于任何功能目标：

- 原始问题必须原样保留；改写只能作为带来源的候选，不能覆盖原问句。
- 原始记录、来源、时间、角色、分支和权限不由模型改写、合并或删除。
- 小管家不是事实来源；每项事实性结论必须能追到当前身份可见的原始记录。
- 时间过滤、身份可见性、授权撤销和来源边界继续由确定性代码执行。
- 不因语义相似就自动认定两条记录是同一事件、同一事实或精确镜像。
- 找不到足够证据时明确返回不足、歧义或需要补充的线索，不用流畅文字掩盖缺口。
- 小管家失败、超时、输出非法或质量下降时，必须能退回现有 records-v1 召回。
- 真实私人数据库和大批量正文不得上传给外部模型服务。
- 小管家在影子验收合格前，不影响 MCP、Telegram 或其他正式回答。

## 3. 目标架构

```text
自然问题
  │
  ▼
问题理解器 / Planner
  ├─ 保留原问句
  ├─ 提取人物、对象、关系、时间和回答意图
  ├─ 列出有限候选解释与子查询
  └─ 标明歧义，不静默猜答案
  │
  ▼
召回编排器 / Orchestrator
  ├─ 精确、时间、原话、来源等确定性路线
  ├─ 有界的改写或语义路线
  └─ 统一轮次、候选和费用预算
  │
  ▼
Echo records-v1 证据层
  ├─ 身份与可见性过滤
  ├─ 原始记录、来源与时间边界
  └─ 现有镜像、阶段、事件与集合规则
  │
  ▼
证据审计器 / Auditor
  ├─ 核对时间范围、来源、冲突和覆盖缺口
  ├─ 区分独立证据、镜像、复述与派生解释
  └─ 拒绝无原文支撑的结论
  │
  ▼
证据简报 / Evidence Brief
  ├─ 有依据的摘要
  ├─ 原始记录引用与可展开正文
  ├─ 未解决歧义和证据不足
  └─ 完整调试轨迹
  │
  ▼
Elion / Telegram 回答模型 / 其他经授权客户端
```

小管家不能被实现为一次大模型调用完成“改写、检索、判断、总结”的黑箱。
上述四个阶段必须有独立、版本化的数据契约和调试输出，才能定位问题究竟来自
问句理解、候选生成、排序、证据审计还是最终表达。

## 4. 阶段计划

里程碑编号只表示建议施工顺序，不表示对应功能已经完成。每一阶段通过自己的
验收门后，才能开始让下一阶段影响正式使用。

### M20：文档真相与考试基线

目标：先固定当前系统真正做了什么，以及以后怎样判断“变聪明而没有变坏”。

工作：

- 重写根 `README.md` 和 `docs/README.md` 的当前架构入口；旧版情绪、向量、
  Saga 与主动浮现能力明确标成 legacy，不再与 records-v1 生产路径混写。
- 画出导入、不可变记录、FTS、MCP、Telegram、错题账和云端快照的当前数据流。
- 整理现有已复核 bad case，并补充成组的自然改写题、精确日期题、原话题、
  来源隔离题、语音错字题、歧义题和覆盖不足题。
- 保存当前生产召回的基线结果、运行时间和候选规模；私人正文仍留在仓库外。
- 建立本路线图的决策日志和状态表。

验收门：

- 新接手的人只看 README 与所链接文档，不会把 legacy 路径误认为当前生产路径。
- 每道已复核题具有期待记录、禁止干扰项或明确的 `unscored` 状态。
- 基线可重复运行，且不会调用外部模型或修改真实数据库。

### M21：小管家契约与无模型影子骨架

目标：先搭出可观察、可关闭的管线，不急着接任何模型。

工作：

- 定义版本化的 `query_plan`、`retrieval_pass`、`evidence_audit` 和
  `evidence_brief` 数据结构。
- 每份计划保存原问句、候选解释、时间约束、关系方向、所需回答类型和预算。
- 用现有确定性 planner 生成第一版计划，证明新管线可以完整复用 records-v1。
- 把小管家置于 feature flag 后，默认关闭；影子输出只进入本地调试与私有错题账。
- 为非法字段、超预算、空计划和内部异常建立失败关闭与旧路径回退。

验收门：

- 开关关闭时，现有 MCP、Bot 和 CLI 的结果与调用次数不变。
- 开关开启但不接模型时，召回结果不低于当前基线，且每一步都能在调试包中解释。
- 删除影子产物不会影响原始记录和正式召回。

### M22：受约束的模型问句理解器

目标：让小模型负责理解自然说法和提出查询计划，而不是负责判断事实。

工作：

- 建立与供应商无关的 planner 接口，不把 DeepSeek、OpenAI 或本地模型写死在核心层。
- 模型只输出严格 JSON；字段、长度、候选数量、时间表达和词项都经过本地校验。
- 原问句始终作为第一条检索路线；模型候选只能追加，不能删除原路线。
- 首版默认只把问句发送给模型，不发送数据库正文。若未来需要基于证据重排，
  必须作为独立里程碑审查最小片段、脱敏、费用和隐私边界。
- 记录模型版本、提示版本、耗时、失败类型和实际采用的候选，但不记录密钥。
- 对提示注入、非 JSON、虚构日期、偷偷补充私人答案和无限拆问建立拒绝测试。

验收门：

- 模型关闭、无 Key、欠费、超时或输出非法时，全部自动退回 M21 路线。
- 模型不能修改时间过滤、身份权限、Top-K 上限和记录内容。
- 相同输入和固定模型输出能重复生成相同的本地执行计划。

### M23：多路召回与证据审计

目标：把“会拆问”变成“能多角度找，但不会乱拼”。

工作：

- 在统一预算内运行原问句、实体关系、时间、原话、公开同义表达等有限路线。
- 按稳定 record ID 和既有 support unit 规则汇合结果；不做语义自动去重。
- 将时间范围、来源要求、角色方向和权限再次作为审计门，而不是相信模型声明。
- 标出独立证据、精确镜像、后来复述、问题/计划、纠正/否认和冲突候选。
- 生成证据简报：结论候选、逐项引用、反证、缺口、未采用候选及其理由。
- 摘要器只能转述证据简报；每个事实句必须携带支持它的 record ID 集合。

验收门：

- 超出明确时间范围的记录不能成为范围内事实依据。
- 禁止记录不能因模型改写或重排重新进入答案。
- 没有证据引用的事实句无法通过 schema 校验。
- 一次回答可以展开到原始记录，且能区分原文与小管家总结。

### M24：影子考试与只读正式接入

目标：先证明小管家整体上优于或等于人工逐步追问，再让它接触正式回答。

工作：

- 对同一批问题同时运行当前基线和小管家路线，不改变对外答案。
- 在已复核错题、未参与调试的新问题和真实生活抽样中比较：目标覆盖、禁止项、
  时间正确性、来源正确性、证据充分度、延迟和费用。
- 让调试面板和 Telegram `/why` 展示原问句、模型计划、实际采用路线、
  Echo 原始证据、审计淘汰项和最终简报。
- 首先在本地 CLI 放行，再依次通过 Telegram 和 MCP 的独立 feature flag 放行。
- 部署继续使用不可变代码版本与快照；保留上一版指针和一键关闭小管家的退路。

验收门：

- 所有已有 `fixed` 且已人工标注期待/禁止记录的错题必须继续通过。
- 精确日期、原话、来源隔离和权限题不得低于基线。
- 自然改写题有可复核的净提升；只让答案变得更流畅不算提升。
- 人工抽查不能发现无证据断言、时间偷换或原文/总结混淆。
- 任一客户端关闭小管家后，可以立即回到当前稳定召回。

### M25：与原始档案隔离的提炼记忆层

目标：允许 Liora、Elion 和经授权的小管家保存整理后的认识，但不污染原始记录。

建议字段：

- 稳定记忆 ID、正文、类型和适用范围；
- 作者身份：Liora、Elion、工具或模型；
- 支撑它的原始 record ID、反证和覆盖边界；
- `draft / active / disputed / superseded / withdrawn` 状态；
- 创建时间、版本、替代关系、审核者和审核时间；
- 独立的 visibility、授权与撤销信息。

工作：

- 使用独立表或独立数据库命名空间；不得伪装成 `records_v1` 原始记录。
- 所有修改形成追加版本，不原地抹掉旧版本。
- 模型只能提交 `draft`；首版只有明确人工审核才能进入 `active`。
- 派生记忆可以帮助规划查询，但不能作为证明真实事件的独立证据；回答仍需追到原文。
- 先开放本地管理命令，再考虑受认证的远程写入口。

验收门：

- 删除整层派生记忆后，原始库、现有召回和云端快照仍可独立工作。
- 任何派生记忆都能查看作者、版本和原始依据；失去证据权限时正文按既有规则受限。
- 撤回或替代不会改写历史，也不会继续以 active 状态参与新回答。

### M26：记忆前台

目标：让非工程视角也能看懂 Echo 为什么这样回答，并管理提炼记忆。

工作：

- 优先复用 M14 调试数据结构，不再造第二套召回器。
- 展示原问句、小管家计划、每轮召回、来源、时间、原文、审计淘汰和覆盖缺口。
- 明确分栏显示“原始档案”“提炼记忆”“小管家临时总结”。
- 支持把结果登记为 bad case，以及审核、撤回或替代提炼记忆。
- 先评估本地 CLI/静态报告是否足够，再决定是否增加 Web UI 与新依赖。

验收门：

- Liora 能一眼判断问题出在问句理解、Echo 召回还是最终回答模型。
- 前台不泄露当前身份不可见的记录、编号或存在性。
- 所有写操作都有明确确认、审计和可恢复历史。

### M27：可选的主动递忆与持续导入

目标：在前述基础稳定后，再增加类似 `breath` 的生活层体验。

候选能力：

- 会话开始时有上限地递出未解决、近期相关或明确置顶的事项；
- 可关闭、稍后提醒或标记不再主动出现；
- 房间结束后进入待审导入队列，而不是未经检查直接写入权威库；
- 计划、信件、长期主题和关系图只作为派生对象，并链接原始证据。

这一阶段不得为了“像人”而主动翻出无关的旧伤、亲密内容或过期工程状态。

## 5. 明确不做的事

- 不训练一颗自有基础大模型；先把现成模型限制在狭窄、可验收的职责内。
- 不用向量库或大模型替换 records-v1 的原始证据层。
- 不让模型凭相似度自动合并、删除或判真原始记录。
- 不把完整私人数据库、大批量对话或长期缓存发送给第三方 API。
- 不为追求主动感而默认开启持续监听、主动消息或无限后台任务。
- 不在错题和影子样本不足时同时增加语音、图像、关系图等新功能。

## 6. 固定验收维度

每个里程碑至少报告以下内容，避免只用“感觉更聪明了”验收：

| 维度 | 需要回答的问题 |
|---|---|
| 目标覆盖 | 人工确认的正确记录是否进入证据包？ |
| 干扰控制 | 已标注的错误记录是否被排除或清楚降为旁证？ |
| 时间正确 | 查询时间范围、消息时间和事件时间有没有偷换？ |
| 来源正确 | GPT、Codex、浏览器抓取和其他来源是否保持门牌？ |
| 角色正确 | “我说过 / 你说过”和历史角色有没有颠倒？ |
| 证据完整 | 摘要里的事实是否逐项有原始记录支撑？ |
| 不确定性 | 没有足够证据时是否明确停下，而不是猜？ |
| 回归 | 已修好的错题是否仍通过？ |
| 隐私 | 发给外部服务的最小数据是什么，是否超出约定？ |
| 可回退 | 能否用一个开关恢复到上一个稳定路径？ |
| 成本与延迟 | 每问调用几次模型、耗时与费用是否有记录和上限？ |

## 8. 防跑偏约定

- 本文件是下一阶段的路线图入口；每次开工先确认当前里程碑和前一验收门。
- 施工过程中出现的新想法先记入对应里程碑的“候选”或决策日志，不顺手扩大范围。
- 改变底线、阶段顺序、外部数据边界或正式放行门槛时，必须在本文件追加理由、
  日期和影响；不得只改代码不改计划。
- 每个里程碑完成时更新状态、提交号、测试结果、真实数据验收范围和回退方法。
- 没有通过验收门不冒充完成；预算或时间用完也不自动降低标准。
