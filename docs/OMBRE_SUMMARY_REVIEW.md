## 查到的实际路线

| 环节 | 当前实现 | 对 Echo 的启发 |
|---|---|---|
| 长内容整理 | grow 自动调用 digest，把长内容整理为事件条目；提示要求 2～6 条，内容与元数据分开，原话另存并关联行号 | 先选择合适的事件窗口；不要默认每一条发言都单独产出一套庞大结构 |
| 历史导入 | 默认提取值得保留的内容，每片 0～5 条；过滤部分调试输出、代码、重复问答等 | 它的紧凑来自有选择地提炼；Echo 应按生活、工程分别定规则，不能据此过滤原始档案 |
| 紧凑目录 | catalog 每条输出名称、域、重要度和足迹等信息，不返回正文，也不调用摘要模型 | 区分目录、摘要卡、详细证据，不把全部存储字段默认递给主助手 |
| 按问题召回 | breath_search 输出已保存的事件正文，当前返回路径不再用模型做一次压缩；超出预算时保留整条边界并给提示 | 读取时少做一次模型调用；同时不能假定整条正文天然很短 |
| 原文证据 | 共享原文可另存、按行号关联；当前公开模型工具移除了 source_read 等入口，原文证据不参与日常召回和向量索引 | Echo 保留独立原文检索和按编号展开；这一点与 Ombre 当前选择不同 |

## 为什么不能直接拿它与第二轮整包大小相比

Echo [第二轮报告](SUMMARY_AUTHOR_ROUND2.md)同时统计了摘要正文和完整结构。
三道长题中，GPT 的事实正文、历史和未知项共占原文字符的 37.1%～42.4%，
但带字段、日期状态与引用编号的紧凑 JSON，占原始正文 UTF-8 字节的 82.3%～100.7%。
这两组计量单位不同，均不是 token 比例；尚未全部通过保真检查的答卷也列入尺寸诊断。

Ombre 的目录和召回输出采用单独的渲染形式，不默认把全部存储元数据原封不动返回。
这支持“后台核验结构与主助手阅读内容分开”的设计；并不证明同题、同覆盖范围下
Ombre 的模型摘要更短、更准，也不能据群内使用反馈直接选定 DeepSeek。

其脱水提示中的“压缩率 > 70%”是目标，不是这次测出来的成绩。
源码还保留了省略主语被归错人物的修复记录，说明角色方向同样需要具体测试：
[提示与历史修复说明](https://github.com/P0luz/Ombre-Brain/blob/115d831d979bf67efc7150f976e2cb34c333c935/src/dehydrator.py#L58-L66)。

## Echo 下一步建议

沿用[摘要优先接入顺序](SUMMARY_FIRST_INTEGRATION_PLAN.md)，不再把查询小管家的全面接入
作为摘要可用的前提：

1. 先用已保存的答卷做本地交付样板：短卡只携带必要内容、来源身份与可展开编号；
   完整事实、历史、状态、日期、引用和复核版本留在后台。不能用隐藏字段掩盖摘要错误。
2. 分开处理独立事件，保留后文纠正、否定和未知项；事件窗口不越过来源、房间或分支边界。
   避免为了压缩把“已买票”和“未来出发”合并成同一个已发生事实。
3. 分别计量后台档案、实际递给主助手的小包，以及展开补查后的总开销。
   用同一原文、同一问题和相同信息要求比较，不能只比一张好看的短卡。
4. 小批合格摘要接原文关键词/向量与展开，再测对主助手是否真的更省上下文、更少漏读。
   查询小管家保留为之后验证增益的可选项。

本次建议没有取消可追溯性要求，没有将摘要替代原文，也没有批准全量摘要生成。
当前正式 Echo 行为保持不变。

后续已按 Liora 的指示做出[短卡与后台档案分层样板](SUMMARY_READING_CARDS.md)，
保留两遍零模型调用的重放结果；包装减重与作者质量分开报告。
