# 共用召回契约审计与小管家影子骨架

审计日期：2026-11-10（成都）。基线为 `b4fab63`；本轮没有更换模型，没有修改
真实数据库，没有把私人原文送往新服务。以下区分机制通过与语义质量尚未验收。

## 已确认的原因

1. MCP 会替省略 `as_of` 的日期问题提供当前参考时钟；Telegram 的本地只读 API
   和调试入口之前没有同样处理。于是无年份的月日问题可能退回不限日期的检索，
   节日和“上周三”可能仍未解释就继续查库。旧测试大多显式传了 `as_of`，
   没有覆盖真正从手机进来的请求形状。
2. 无效日期曾被误当作没有日期要求；中文月日前的年份、相对年份和节日前的年份
   可能被忽略；多日期问题只取第一个表达。
3. 覆盖保护把 UTC 时间字符串截成日期，与成都的查询日期直接比较，可能误挡住
   UTC 深夜、成都已到下一天的记录。
4. 错题重新运行时没有固定原问题的参考时钟，同一条“上周三”隔周就可能变成另一道题。
5. 返回数量有界不代表响应体积有界。原文、相邻上下文、时间线和调试信息会重复扩张。

不能把以上全部归因于回答模型。当前 Bot 交给末端模型的是主召回项的有限正文片段，
并没有把相邻上下文与范围外复述全部喂进去。MCP 的大包与 Bot 的片段截断是两个
不同问题，后续应由共享的证据简报解决。

## 本轮修复的共用约束

- `adaptive_recall` 为需要参考日期而未提供 `as_of` 的请求统一取得带时区服务器时钟；
  显式传入的有效时钟仍优先，记录来源供复核。纯日期解释器本身不读系统时钟。
- 明确年份优先于参考年份；相对年份按参考时钟解释。
- 无效、当前不支持的节日年份和多日期表达返回明确待澄清状态，检索轮次为零，
  不再偷偷退回全库检索。当前尚未支持任意多日期并集或区间解释。
- 日期待澄清时，Bot 直接展示共用说明，不调用回答模型；CLI、MCP 指引及新错题包
  保留该原因，不能显示成“缺少主题”或“记忆不存在”。
- 覆盖截止时间先换为成都日期再比较；保留记录时间与事件时间的区别。
- 错题 CLI 优先使用包内原查询时钟，次选时间线时钟，再选标明代理性质的采集时间。
  可以用 `--as-of` 明确覆写；没有锚点的相对日期回放会拒绝。原错题包不被修改。

## 无模型影子做什么

通过本地 `scripts/recall_debug_cli.py --caretaker-shadow` 显式开启；默认关闭。
只在原来的一次有界召回旁附加以下四份版本化对象：

| 对象 | 当前内容 |
|---|---|
| `query_plan` | 原问题、记录日期范围、固定预算；不执行模型改写 |
| `retrieval_passes` | 原召回已实际执行的轮次与结果数量；不再检索 |
| `evidence_audit` | 主记录的日期、来源引用、提及类型、排除理由；不声称语义充分 |
| `evidence_brief` | 最多 10 条、每条最多 320 字符、合计最多 3200 字符的原文前缀摘录 |

摘录携带 record ID、原记录长度、字符偏移和截断标记；`source_excerpt` 不冒充模型
摘要。这里的 3200 是**摘录正文字数上限**，不是完整 JSON 或模型 token 上限。
JSON 元数据和最终 token 预算须在模型接入前单独约束。完整原包依然保留，所以打开
影子开关本身不会使现有 MCP 响应变小。

相邻上下文和范围外复述只计数，不升级成主简报事实。异常、超预算或非法计划时标记
`failed_original_preserved`，保留原召回结果。关闭开关无需数据库迁移或清理。

合成库演示：

```bash
python scripts/admin_cli.py --db-path ./demo-v1.db --yes register-agent --agent-id agt-demo --display-name Demo --actor demo
python scripts/import_history.py tests/fixtures/echo_pact_records_v1.json --db ./demo-v1.db --owner-agent-id agt-demo --actor demo
python scripts/recall_debug_cli.py "记忆问题" --db ./demo-v1.db --agent-id agt-demo --caretaker-shadow --json
```

真实库路径、身份和输出应使用本机已有私人配置。原文与整份调试 JSON 不进入公共
仓库，也不为了验证模型而批量上传。

## 验证范围与尚未解决的问题

- 新增无 `as_of` 的 MCP、Telegram 本地 HTTP 与 CLI 共用函数对照，包含普通月日、
  中文月日、节日和上周几。初次复现 11 项失败，修复后通过。
- 合成题还覆盖显式/相对年份、无效日期、多日期、UTC 跨日边界、原时钟回放、
  影子开关、原文偏移、排除理由、无模型调用与失败回退。
- 最终全量测试 528 通过、1 跳过；跳过项未作为通过项计数。另有四条既有依赖
  弃用提醒，没有在本轮顺带升级依赖。
- 真实库只读抽检四类日期问题：两入口主记录 ID 一致，主记录时间都在指定范围，
  操作前后数据库哈希一致。没有对真实事件的目标记录做人工评分，状态是 `unscored`。
- 四题当前 MCP 完整包约 10.5 万至 14.7 万字符；影子摘录正文约 2964 至 3200 字符，
  简报 JSON 约 0.86 万至 0.90 万字符。这只是旁路体积测量，不代表正式上下文已经缩小。
- 日期概览仍偏向每个会话的最终正文及较长记录，四题各 10 条里有三题全是 assistant。
  “时间范围正确”不等于“当天最重要的事件都找到了”，这部分不能宣称已修好。
- 事件发生日、消息记录日、后来复述日仍需分开；有限节日表、自然问题改写、语义
  排序、全文展开及完整人工错题考试集留在后续阶段，不继续堆 Bot 专用规则。

下一步先补已复核目标与干扰记录的考试集，再选模型接入共享 Planner/简报器。
模型摘要必须与原档案分开，逐项有出处；拒答、漏项或失败要显式呈现并保留原文退路。
