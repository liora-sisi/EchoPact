# 中文试卷输入损坏：勘误与复验

2026-11-25。接续[真实旧题验收](SEMANTIC_REAL_ACCEPTANCE.md)。

**上轮“新问法排名从 4 掉到 286”不是有效的自然语言对照。** 新问法在 Windows
PowerShell 5.1 向 Python 输送脚本时被替换成了二十二个 ASCII 问号；模型实际收到的也
是这些问号。原始记录、向量索引及从已有 UTF-8 文件读取的两道旧题没有被该管道改写。

## 已核实的根因与影响

现场 `$OutputEncoding.WebName` 是 `us-ascii`。仅设置 `PYTHONUTF8=1` 不会改变
PowerShell 发送端的编码：Python 收到问号后已经无法恢复原来的字。
旧私有 scope、冻结 API 请求和规划响应均保存着损坏输入，证据链一致。

- 新问法：原意二十二字符，实际二十二个问号，汉字数为零。
- 日期/来源两个对照也有汉字丢失；剩下的数字或 GPT 字母碰巧触发了原路线保护，
  不能把这些结果算作完整中文日期/来源题验收。
- 两道旧题从既有文件读取，汉字完整，其原文命中和对象初选遗漏仍是有效观察。
- 问号的向量排名发生在 RRF 合流之前。因此，旧结果既不能证明切块断义，
  也不能证明词面/向量权重不当，更不能据此认定规划模型误拒正常问题。
- 此前的“1/3 目标可见”不能作为三道有效问法的得分。有效旧题只有两道，其中一道
  部分目标可见；这仍不是完整答案准确率。

旧卷、失败调用及费用全部保留，不覆盖、不重写成成功。上轮提示 v4 与原问退路的
机制代码仍有各自回归检查，但不能把乱码题的结果当作它们改善语义质量的证据。

## 修复

1. `query_caretaker.validate_question` 拒绝完全不含字母或数字的输入；
   `run_shadow` 在第一次查询之前执行检查，API 请求构建同样使用该验证。
2. 分阶段试验另加严格输入检查，拒绝替换字符及连续 ASCII 问号。
   这是人为编写试卷的校验，不把普通聊天里的问号自动改写成猜测的文字。
3. 冻结请求附带不含问题正文的文字回执：字符数、UTF-8 字节数、汉字数、问号数及
   UTF-8 摘要。后续调用重新核对回执；内容损坏时不建立试验目录、不调用模型。
4. 优先直接执行 UTF-8 文件。确需 PowerShell 原生管道时，在该次命令里显式设置
   `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`，并用预期 Unicode 字符核验。
   已用含中文、重音字母与 emoji 的合成文本验证往返，未修改系统配置或 PowerShell 配置文件。

这不能识别所有可能的乱码；固定题的人工字面核对和来源校验仍不可省略。
