本阶段接通已有问句理解、只读检索和证据复核；没有进入正式 MCP、Telegram 或真实摘要柜。

## 这次接通什么

```text
原问句先查一次 → 问句模型只提取原问中的主题与意图
                 → 本机最多追加两次查询
                 → 单主题对象比较：有限对象补查 → 一次对象证据复核
                   其他合格问题：             → 一次通用证据筛选
                 → 逐字核对引用、来源与容量 → 带出处及缺口的短证据
```

两个证据复核分支互斥，一问最多一次问句模型、一次证据模型。日期、首次、原话、来源、
否定及其他尚不支持的约束沿用原路线，不因配置了模型就丢掉限制。没有线索、模型关闭、
失败或计划不合格时，也不会偷偷转入另一次模型调用。

实现为 `backend/memory/caretaker_pipeline.py`，供应商通过回调注入。模块不持有钥匙、
网络客户端或自动重试逻辑，也没有注册进生产入口。`readonly_pipeline(db_path, agent_id)`
把普通召回和对象扫描绑定到同一个只读库、同一个固定身份；模型不能改路径、身份、
参考时间或条数上限。

最多三次 gateway 调用加两次对象扫描，失败尝试也计数。这是**五次入口操作上限**，
不是五条 SQL；原有 gateway 内部仍可能有自己的有界检索步骤。

跨阶段观察到同一来源时，会核对身份字段、角色、记录时间和文字。明确标记的截断前缀
可以与完整原文一致，变更或冲突则阻止后续证据复核。它检查观察一致性，不判定原文真伪。
后续失败保留 M22 已有短包；连首次原问召回都失败则返回固定错误，不捏造空答案或泄露异常正文。

## 递给助手与留给调试的内容分开

返回对象的 `brief` 才是拟递给助手的内容。`audit` 保存原召回、追加查询、候选和模型判断，
留在本地私有验收材料；`trace` 记录实际入口操作与模型回调次数。不能把整个返回对象
直接接成 MCP 响应，否则会把完整调试包再次倒入上下文。

证据筛选后的短包仍是**模型挑选、本机逐字核验的原文摘录**，不是模型改写后的事实摘要。
最多六项、12,000 UTF-8 字节，并保留来源、字符偏移、截断、覆盖和未解决歧义。
模型声明“充分”不会覆盖确定性的覆盖不足标记；关系组装不全时也不能只递半边。
未运行筛选或失败时保留既有 M22 短包及其独立上限，不冒充筛选成功。

当前几个入口的差别：

| 入口 | 首次收到什么 | 是否使用这条模型整链 |
|---|---|---|
| MCP 显式 `detail="brief"` | 编号、来源、短原文预览；再按需 `expand_record` | 否 |
| MCP 兼容旧调用，未指定 detail | 完整审计视图，默认仍为 `full` | 否 |
| Telegram 回答模型 | 有界原文摘录；当前私人配置最多五条、每条最多 1,200 字符 | 否 |
| Telegram `/why` | 上一轮最多十条召回的原文预览及送模标记，不重新召回 | 否 |
| 本机小管家整链试验 | 上述 `brief`，完整现场留在本机 `audit` | 仅显式注入模型时 |

MCP 的短目录不是预计算摘要柜。入库后预先写摘要属于独立的 M21B，真实档案尚未启用。

题后没有改提示或金标准，原始响应另存。模型请求不含金标准，也没有真实档案内容。

| 虚构问题 | 实际检查到的结果 | 递给助手的短包 / 原始首次召回 |

两题的预设目标、禁止项、来源引用、路线和模型充分度检查均通过。人工逐项核对实际文字后，
确认两题正确引文保留。对象题的复核模型看到两张卡；步骤题经本地检索与筛选后只剩一张卡，

不是生产准确率，也不是大规模独立盲测。** 历次失败和严格成绩保持原样。

## 下一关与退路

  本轮没有主分支合并、服务切换或真实数据库写入。
